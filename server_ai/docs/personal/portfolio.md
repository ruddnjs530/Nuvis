# 🏆 포트폴리오 (Portfolio)

**프로젝트 명:** 스마트 홈 로봇 (자율 주행 및 홈 IoT 통합 관제 시스템)
**담당 역할:** AI Engineer & ROS2 Vision Developer & Backend Developer

---

## 1. 프로젝트 개요 (Overview)
사용자가 웹 대시보드를 통해 집안의 환경(온도, 습도, 미세먼지)을 실시간으로 모니터링하고, 자율 주행 로봇과 연동된 IoT 모듈(공기청정, 가습, 제습, 에어컨)을 스마트하게 제어하는 시스템. **AI 파트와 백엔드 메인 서버를 동시에 전담**하여 "비전(Vision) 기술을 통한 환경 인지", "데이터 분석을 통한 스마트 추천", "자연어 기반 음성 제어" 등 핵심 지능형 기능을 구현하는 동시에, **AI 서버 ↔ 백엔드 서버 간 연동 아키텍처를 직접 설계·문서화하고 양측 구현을 모두 담당**했습니다.

또한 모노레포 구조 설계 과정에서, **추천 AI와 STT는 `server_ai` 독립 서비스로 분리**하고, **YOLO 비전은 ROS2 런타임에 더 가까운 노드로 판단하여 추후 `ros2_ws` 측으로 재배치**하는 역할 경계도 직접 정리했습니다. 여기에 더해, **일반 서버(Docker / Jenkins)와 GPU 서버(`server_ai`)를 분리하는 배포 전략**까지 문서화하여 백엔드 / 인프라 협업 기준을 수립했습니다.

## 2. 주요 구현 기능 및 성과 (Key Achievements)

### 📸 2.1 실시간 장애물 탐지 비전 관제 (Vision)
*   **문제**: 로봇이 실내 자율주행 시 동적인 방해물(사람, 반려동물, 물건 등)을 식별하고 멈춰야 함.
*   **해결**: ROS2 환경(foxy/humble) 기반으로 로봇 전방 카메라 센서(`image_raw` 토픽) 이미지를 Subscribe하여 **YOLOv8 Object Detection** 모델로 넘기는 Python Bridge Node(`yolo_node.py`) 설계.
*   **성과**: 실시간(Real-time)으로 객체 위치(Bounding box)를 파악하고 장애물 발견 시 주행 파트 노드에 멈춤 신호를 Publish 할 수 있는 비전 파이프라인 구축. 모델 경량화 및 추론 최적화를 고려한 설계 제공.
*   **아키텍처 정리**: YOLO는 일반 AI API 서버 기능과 분리하여, 최종 모노레포 기준으로는 `server_ai`가 아닌 `ros2_ws` 측 비전 패키지로 운영하는 방향을 정리.

### 🧠 2.2 사용자 맞춤형 AI 추천 시스템 설계 및 구현 (IoT Data Recommendation)
*   **문제**: 유저가 스마트 홈 이벤트를 일일이 등록하기 번거로우며, "쾌적한 상태"의 기준은 유저마다 다름. 또한 AI 서버와 백엔드 서버 간 효율적인 데이터 연동 아키텍처가 필요함.

*   **해결 — 알고리즘:**
    `Pandas` 기반 통계 분석 파이프라인 구축. 과거 실내 환경 데이터(온도, 습도, 미세먼지)와 유저의 모듈 ON/OFF 로그를 분석하여 유저 쾌적도 기준치를 역추적하는 **Rule-base & Stat-base 임계값 추천 알고리즘** 구현. (`recommendation/main.py`)
    - **이벤트 기반 추천:** 환경 수치 이상 탐지 시 최적 임계값 추천 (`POST /api/event/ai-suggestions`)
    - **스케줄 기반 추천:** 사용자의 기기 사용 시간 패턴 분석으로 반복 일정 자동 추천 (`POST /api/schedule/ai-suggestions`) — 설계 완료, 구현 예정

*   **해결 — 아키텍처:**
    AI 서버가 DB에 직접 접근하지 않고, 백엔드 서버가 필요한 데이터를 추출하여 API 페이로드로 전달하는 **Stateless API (Data Passing)** 방식을 직접 설계 및 문서화. 인터페이스 계약(Contract)을 명세화하여 병렬 개발 가능하도록 제안하고, 양측 구현을 직접 담당.

*   **해결 — DB 설계 기여:**
    백엔드 ERD를 검토하여 AI 패턴 분석에 필수적인 **시계열 이력 테이블 2개** 추가를 직접 설계 및 반영:
    - `ROOM_CONDITIONS_HISTORY`: 센서 값을 덮어쓰지 않고 누적 저장하는 이력 테이블
    - `MODULE_CONTROL_LOGS`: 실제 기기 가동/정지 시각이 기록되는 조작 로그 테이블

*   **성과**:
    - 유저 과거 데이터 기반 5% 안전 마진(Safety Margin) 적용 최적 임계값 계산 → FastAPI 엔드포인트로 백엔드 서버에 제공.
    - 공기청정기/가습기/제습기/에어컨 등 **모든 기기 타입에 동일한 AI 로직 재사용 가능**한 확장성 검증 (ERD의 `VARCHAR` 기반 타입 컬럼 활용).
    - Human-in-the-loop → Full-Automation 두 단계 상용화 로드맵 설계 (MVP 안정화 후 완전 자율 제어로 고도화 가능한 구조).
    - 일반 서버 Docker 배포와 GPU 서버 AI 분리 운영, Jenkins 서버별 배포 흐름까지 포함한 **실서비스 배포 전략** 문서화.

*   **해결 — 서비스 강건성 강화 (`2026-03-13` 추가):**
    Stateless API 아키텍처의 잠재적 취약점을 자가 진단하고 다음 3가지 안전장치를 코드에 직접 적용:

    | 안전장치 | 구현 방식 | 효과 |
    |---|---|---|
    | **페이로드 상한선** | `sensor_data[-MAX_RECORDS:]` (최신 500건만 사용) | 대량 이력 전달 시 메모리/처리속도 저하 방지 |
    | **기기별 독립 타임아웃** | `asyncio.wait_for` + `asyncio.to_thread` (기기당 5초) | 1개 기기 분석 실패가 전체 응답 실패로 전파되는 것 차단 |
    | **Fallback 응답** | 타임아웃/오류 시 기기별 개별 fallback 메시지 반환 | 부분 장애 시에도 정상 분석된 기기 결과는 그대로 제공 |

    > 두 상수(`MAX_RECORDS`, `ANALYSIS_TIMEOUT`)를 파일 최상단에 분리 선언하여 운영 중 튜닝이 필요할 때 코드 한 줄 수정만으로 조정 가능하도록 설계.

### 🎙️ 2.3 음성 인식(STT) 기반 로봇 제어 통합 (Voice Command Parsing)
*   **문제**: 대시보드 클릭 등 GUI 방식 외에, "거실 가습기 켜줘"와 같은 직관적인 음성 명령 제어가 필요함.
*   **해결**: **OpenAI Whisper** 모델을 로컬 환경에 파이프라인으로 구성하여 녹음된 사용자 음성을 텍스트로 고정밀 STT 변환 테스트 진행. (`stt/whisper_test.py`)
    변환된 자연어 문자열을 분석하여 목표 장소(거실, 주방)와 수행할 행동(이동, 모듈 전원 ON)을 분리해내는 Python 파서 엔진 구축 (`stt/stt_parser.py`)
*   **성과**: 비정형 자연어 데이터를 시스템이 읽을 수 있는 정형화된 JSON 형태의 제어 명령으로 치환하여 로봇-인간 상호작용성(HRI) 극대화.

### 🔵 2.4 백엔드 메인 서버 개발 (Backend Server)
*   **문제**: IoT 센서 데이터 수집, 이벤트/스케줄 룰 엔진, AI 서버 연동, 로봇 명령 하달을 담당하는 메인 서버가 필요함.
*   **담당 범위**:
    - IoT 센서 데이터 수신 및 DB 저장 API 구현
    - 이벤트 조건 판단 및 스케줄 실행 룰 엔진 구현
    - AI 서버 HTTP 클라이언트 모듈 (Timeout 30초, Fallback 처리 포함)
    - AI 추천 결과를 사용자에게 제안하고 수락 시 DB에 반영하는 Human-in-the-loop 파이프라인
*   **성과**: AI 서버와 백엔드 서버를 동시에 담당함으로써 연동 인터페이스를 스스로 정의하고 양측을 직접 맞춰가는 **Full-Stack 연동 경험** 확보. API 계약 명세서(`api_contract.md`)를 통해 타임아웃·Fallback 정책 등 운영 상황에서의 예외 케이스를 사전에 설계.
    추가로 Jenkins를 포함한 분리 배포 전략까지 정리하여, 개발 단계의 프로토타입을 실제 운영 가능한 배포 구조로 연결하는 기준 문서를 구축함.

## 4. 팀 회고 및 배운 점 (Retrospective)

- **역할 범위 재정의 경험**: 처음에는 SLAM과 Navigation 파트까지 AI가 맡아야 하는 줄 알고 구조를 설계했으나, 스펙 문서를 깊게 분석한 후 `순수 컴퓨터 비전/ML 처리` 영역과 `로보틱스 측위(Positioning)/이동 제어` 영역을 분리하여 협업 효율을 극대화함.

- **AI 서비스와 ROS2 비전 노드의 경계 설정 경험**: 추천 AI와 STT는 백엔드가 호출하는 `server_ai` 독립 서비스로 두고, YOLO는 카메라 토픽과 밀접한 ROS2 비전 노드로 분리하는 방향을 정리함. 기능 단위가 아니라 실행 맥락 단위로 책임을 나눈 경험을 확보함.

- **Cold Start 문제 해결 경험**: 프로젝트 초반 실 데이터가 없는 환경을 극복하기 위해 더미 데이터 모의 생성기(`generate_mock_data.py`)를 개발하여 메인 서버 및 알고리즘 검증을 블로킹 없이 병렬로 진행하는 능력을 기름.

- **시스템 설계 및 팀 간 기술 협의 경험**: AI 서버가 DB에 직접 접근하는 방식 대신, 백엔드 서버가 데이터를 추출하여 전달하는 Stateless API 방식의 장단점(응답 속도, 서버 부하 분산, 확장성)을 직접 분석하고 연동 표준으로 제안. 단순 코딩을 넘어 **서버 간 인터페이스 계약 설계** 역량을 키움.

- **DB 설계 기여 경험**: 단순히 AI 알고리즘 구현에 머무르지 않고, ERD를 직접 분석하여 AI 모델이 필요로 하는 데이터 구조(시계열 이력)가 누락되었음을 능동적으로 파악하고 테이블 설계 및 추가를 직접 반영하는 Cross-functional 경험.

- **인프라 제약 극복 경험**: 보안 웹 환경(JupyterHub)의 포트 차단이라는 인프라 제약을 파악하고, SFTP 대신 `git sparse-checkout`으로 GPU 서버 배포 전략을 전환하여 외부 의존성을 최소화한 안정적인 워크플로우를 구축함.

- **아키텍처 강건성 개선 경험**: 단순 코딩 완성에 머물지 않고, 기존 Stateless API 설계의 잠재적 취약점(페이로드 폭발, 장애 전파)을 스스로 진단하고 `MAX_RECORDS`(페이로드 상한), 기기별 `asyncio` 타임아웃, Fallback 응답 패턴을 코드에 직접 적용. **아키텍처 감사와 지속적 개선** 습관을 키움.

- **AI + 백엔드 Full-stack 연동 경험**: AI 서버와 백엔드 서버를 동시에 담당하면서 연동 인터페이스의 양측을 모두 직접 설계하고 구현. API 계약, 타임아웃 정책, Fallback 처리를 한 사람이 end-to-end로 결정하고 적용하는 경험을 통해 **서버 간 통신 설계의 전체 맥락**을 이해함.

- **분리 배포 전략 수립 경험**: "Docker로 통합 배포"와 "GPU 서버 분리 운영"이 충돌하지 않음을 구조적으로 정리하고, Jenkins 기준으로 일반 서버와 GPU 서버를 각기 다른 방식으로 배포할 수 있도록 문서화함. 이를 통해 인프라/백엔드 협업에서 자주 혼동되는 배포 개념과 실행 위치를 명확히 분리하는 경험을 확보함.
