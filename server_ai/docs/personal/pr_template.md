# 📝 Pull Request (PR) 템플릿 & 작성 가이드 레퍼런스

이 문서는 앞으로 프로젝트에서 Github/Gitlab에 Pull Request(Merge Request)를 올릴 때 사용할 수 있는 **표준 템플릿**과 **상황별 예시**를 모아둔 개인 레퍼런스입니다. 
PR 작성 시 이 양식을 복사하여 상황에 맞게 수정해 사용하세요.

---

## 📌 PR 기본 템플릿 (복사해서 사용)

```markdown
## 1. 💡 개요 (Description)
- 어떤 이유로 이 PR을 작성하게 되었는지 간략하게 설명합니다.
- 관련된 이슈 번호가 있다면 링크를 걸어주세요. (예: `Resolve #123`, `Fixes #45`)

## 2. 🚀 주요 변경 사항 (Key Changes)
- [ ] 작업 내용 1 (예: Whisper 기반 STT API 구현)
- [ ] 작업 내용 2 (예: 테스트 자동화 스크립트 작성)
- 코드의 어느 부분이 어떻게 변경되었는지 핵심 위주로 요약합니다.

## 3. 📸 스크린샷 및 테스트 결과 (Screenshots / Test Results)
- UI/UX 변경사항이 있다면 스크린샷이나 GIF를 첨부해주세요.
- 백엔드/AI 로직 변경이라면 Postman 실행 결과, 서버 로그, 벤치마크 점수 등을 텍스트나 캡처로 첨부하세요.
- 예: "STT 벤치마크 테스트 결과 정확도 100% 달성 (7/7)"

## 4. 🤔 리뷰 요청 사항 (Review Requests)
- `stt_parser.py` 파일의 정규식 처리 부분이 효율적인지 중점적으로 리뷰 부탁드립니다.
- 프론트엔드 연동 시 API 엔드포인트가 맞게 호출되는지 확인이 필요합니다.

## 5. 🔜 향후 계획 (Next Steps)
- 본 PR 머지 이후에 이어서 진행해야 할 작업이 있다면 작성합니다.
```

## 🛠️ 상황별 예시 (Examples)

### 1) 신규 기능 개발을 완료했을 때 (Feature)
**[제목]** `feat(AI): 음성 명령 기반 로봇 제어 명령어 파싱 기능 추가`
**[개요]** 사용자의 음성을 텍스트로 변환한 뒤, 로봇 제어용 JSON 포맷으로 생성해주는 `stt_parser` 기능을 새롭게 개발했습니다.
**[주요 변경 사항]**
- `ROOM_MAP`, `MODULE_MAP` 딕셔너리를 활용해 대상 기기와 위치 추출 로직 작성
- 부정어 처리를 위한 정규표현식 로직 추가
**[리뷰어에게]** 새로운 가전 기기가 추가될 경우 `MODULE_MAP`에 추가해야 하는데, 이 방식이 나중에 확장하기 좋을지 의견 부탁드립니다.

### 2) 버그를 수정했을 때 (Bug Fix / Hotfix)
**[제목]** `fix(STT): '가습기 꺼줘' 명령에서 '공기청정기'로 오인식되는 버그 수정`
**[개요]** Whisper 모델이 발음이 비슷한 단어를 오인식하는 문제가 발견되어, 이를 보정하는 로직을 추가했습니다. (Resolve #15)
**[주요 변경 사항]**
- Whisper 추론 옵션에 `initial_prompt`를 주입하여 도메인 특화 단어 인식률 개선
- 예외 처리 구문 강화
**[테스트 결과]** 해당 옵션 적용 후 기존 85% 정확도에서 98%로 향상됨.

### 3) 코드 রি팩토링 또는 성능 개선 (Refactor / Perf)
**[제목]** `refactor(AI): STT 모델 벤치마크 스크립트 모듈화 및 속도 개선`
**[개요]** 테스트 스크립트 파일이 너무 커져 유지보수를 위해 구조를 분리하고, 불필요한 연산을 줄였습니다.
**[주요 변경 사항]**
- `test_client.py`의 통신 로직을 별도 클래스로 분리
- 모델 로드 과정을 싱글톤 패턴으로 변경하여 추론 속도 20% 향상

### 4) 문서 작업만 했을 때 (Docs)
**[제목]** `docs(AI): AI 서버 환경 설정 가이드 및 API 명세서 최신화`
**[주요 변경 사항]** `README.md` 내의 로컬 구동 방법과 Swagger API 명세 스크린샷을 최신 버전으로 업데이트했습니다.

## 💡 PR 작성 꿀팁
1. **작게, 자주 올리기**: PR 하나에 너무 많은 변경(수천 줄)이 담기면 리뷰어가 보기 힘듭니다. 기능 단위로 잘게 쪼개서 올리세요!
2. **커밋 컨벤션 지키기**: `feat`, `fix`, `docs`, `refactor`, `chore`, `test` 등 접두사를 통일하면 로그 보기가 편해집니다.
3. **내 코드 먼저 셀프 리뷰하기**: PR을 올리기 전 깃허브의 'Files changed' 탭에서 내가 짠 코드를 한 번 쭉 읽어보면 사소한 실수를 짚어낼 수 있습니다.
